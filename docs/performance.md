# 列表、预览与同步性能

2026-10-23 的本机合成数据测试如下。三次运行取中位数，使用已收集的索引和文件缓存；不读取用户历史，不启动 Agent，不发送模型请求。

| 场景 | 原读取方式 | 优化后 |
|---|---:|---:|
| 1001 个文件：项目选项与列表读取 | 897 ms，完整读取两次 | 9.4 ms，项目元数据与前 500 行 |
| 20000 条消息：首次预览读取 | 103 ms，解析全文 | 2.7 ms，读取最近 400 条 |
| 展开末尾的工具记录 | 67 ms，按序号从头读取 | 0.29 ms，按字节位置定位 |

这些数值只包含数据读取，不包含窗口创建、Markdown 排版和首次全库索引。真实耗时取决于磁盘、文件长度、分支数量和缓存状态，回归测试不以机器相关的耗时阈值判定成功。

复现命令：

```shell
python tests/benchmark_reading.py --files 1000 --messages 20000 --repeat 3
python -m unittest tests.test_read_performance -v
```

## 列表与搜索

项目下拉框直接读取收集后的目录元数据。界面按数据库中的完整结果排序、过滤并分页，不再为每个页面检查所有无关原生文件。排序跨页时会扩大已加载范围以保留选中或勾选的项目。逻辑对话只按登记的物理身份归组；归组需要检查已登记版本及分支，成本仍随这些版本数量增加。

界面启动时先显示上次收集的列表，后台再发现新增、改动和删除的文件。打开正文和启动会话仍校验当前原生文件；列表缓存不作为清理或释放会话预约的依据。显式“刷新历史”继续执行完整发现和同步。

数据库版本 4 增加按物理文件区分的全文索引，以及文件到会话的查询索引。正文搜索用三个字符的索引项筛选候选，再核验大小写折叠后的精确子串；不足三个字符的搜索保留子串回退。独立的同 ID 文件、祖先内容和自定义标题继续分别匹配。

旧数据库打开时只建立索引结构，已有搜索文本在后台收集时分批补齐。尚未补齐的文件直接进行子串匹配，因此补齐期间不会漏掉旧内容。只同步一条会话时，也只补齐相关文件的搜索索引。搜索索引使用已有缓存文本作为外部内容，不再保存一份正文；仍会增加词项索引占用。

插入、更新和删除触发器维护全文索引，兼容升级前收集进程使用的 `INSERT OR REPLACE`。它们只维护应用数据库，不改变原生历史文件。

## 正文与工具详情

首次预览从 JSONL 尾部读取最近一页，加载更早消息时再读取前一页。游标同时记录原生分支链、记录字节位置和消息边界，支持一个 Claude 记录中的多条消息跨页。原生祖先的字节与序号截止标记同时有效；序号边界首次可能需要扫描前缀，随后按文件变化标记复用边界缓存。末尾未完成的记录不参与预览。

工具详情直接定位到完整原记录，保留读取前后的文件变化校验。旧序号定位仍可读取。Ctrl+F 搜索完整对话时在后台加载全文，保持较早消息可搜索；全文加载和 Markdown 排版仍可能花费时间。加载更早消息和切换预览格式保留当前阅读位置。

2026-10-23 后续优化：Ctrl+F 输入合并等待 150 ms，在后台定位匹配消息；全文数据可读，但每次仅排版命中附近最多 400 条消息，上一处／下一处支持跳转到相距很远的匹配。当前窗口的高亮分批执行。读取、定位和显示结果分别提示，测试等待实际任务与渲染阶段，不再用搜索提示的五秒期限代替渲染完成。

正常分页向前加载时只插入新的一页，已显示的工具面板及展开结果继续使用；代码高亮与消息标记随阅读位置一起保留。表格的测量与绘制按行让出界面线程。版本信息、分支及展示用启动选项在后台计算，真正点击启动仍检查当前原生状态。纯读取使用最多四个工作线程；同步、合并和清理继续使用各自的任务与锁。

快速切换搜索或对话时，过时读取在安全边界停止；旧结果不会覆盖新选择。取消仅用于读取和排版，不中断同步、索引事务或可恢复清理。

## 启动报告与同步状态

完成的启动报告在进程内缓存；活跃、待同步任务继续检查。原子发布改变目录时间时重新发现报告，并每五秒完整核对一次，以兼容旧程序直接覆写报告。历史报告保留在原位置。

使用旧报告快照更新采集状态时，同时核验任务状态、进程身份、尝试次数和更新时间，防止旧检查把重新运行的任务标成已采集。同步状态显示等待历史任务、校验内容、原生恢复验证、回收覆盖版本、更新索引或等待原生写锁等阶段，并记录最近成功同步时间。异常退出、旧任务缺少退出码、独立分支和原生锁的保护规则继续生效。

## 长文件追加、分组缓存与失败重试

数据库版本 5 为可重建的阅读缓存增加追加检查点与搜索片段。无祖先链的 Codex／Claude 文件只有在整个已索引前缀通过哈希核验、检查点一致且读取期间文件未变化时才增量解析；完整前缀只读一次，并复用哈希状态处理新增字节。搜索只索引新片段，片段前保留两个字符，保证跨消息边界的三字符候选不遗漏；最终仍核对完整精确子串。重写、截断、祖先变化或检查点失效时完整重建，原生恢复及回收校验独立执行。完整搜索文本仍需拼接，片段文本和索引会增加缓存空间；运行较早版本的进程仍可通过原全文索引及未覆盖回退查询。

版本 6 修复早期中间版 v5 与最终 v5 使用相同版本号的问题：打开数据库时核验实际索引表、触发器和外部内容配置，而不只检查版本号。缺少片段覆盖或逻辑修订时，先在迁移锁内完成可重建索引结构升级，再允许列表和采集查询；完整 v5 只更新版本标记。该迁移保留逻辑对话、不可变修订、导入映射、删除记录与预约，多个并发打开者等待同一次升级。环境诊断也显示索引结构是否已就绪。

同机合成 20000 条消息、每次追加一条，三次中位数：强制完整重建阅读索引约 234 ms，追加维护约 57 ms。测试仍执行完整前缀校验，包含指定路径采集和搜索更新，不含模型执行、跨平台转换或原生 resume 验证。复现沿用上方 benchmark_reading.py 命令；这一比较针对本轮优化前后的追加索引成本。

逻辑分组按数据库修订、接入范围、候选身份及原生文件是否存在缓存，版本投影只重新解析变化的逻辑对话；文件删除、修订、合并或活动版本变化会使结果失效。每次读取仍验证连接身份和文件存在性，此缓存只用于显示。查询入口及分组内部均支持过时读取取消。

采集按物理文件隔离读取异常，失败文件保留已有索引，并在数据库记录阶段与原因；其他文件继续更新。界面提示待重试数量，右栏显示具体原因，“重试失败索引”仅采集失败路径。退出收尾只有相关索引通过后才报告完成并释放预约。正在追加或末尾未完成的 JSONL 可保留并稍后重试。

## 本机性能诊断

“诊断与维护”的报告增加当前进程及最近最多 32 个进程的数值统计，包括列表、阅读、搜索、排版、启动选项、采集、同步与锁等待的次数、累计／最大／最近耗时，以及部分阶段的文件和消息数量。进程写入自己的小型统计文件，位于私人运行目录的 performance 子目录，工作线程最多每秒发布一次。仅接受固定阶段名和数值计数，不记录查询、正文、命令、路径或认证内容；复制与导出继续使用脱敏字段。
