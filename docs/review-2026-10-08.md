# 项目 Review：可靠性、性能与维护

日期：2026-10-08。审查基线：`9524ba2`。本轮为代码审查和隔离复现，不实施功能修改，不调整 roadmap 的完成状态。

审查覆盖采集／检索、物理版本与逻辑对话、临时接续生命周期、删除／恢复、任务报告、UI 读取及启动、配置与安装。所有故障注入只使用系统临时目录和合成会话；未删除或改写真实历史，未读取认证文件，未发送模型请求。以下“数据丢失”是模拟故障下可复现的代码行为，不表示已经发现用户真实会话丢失。

基线曾通过 126 项单元／隐形 Tk 检查和 4 项隔离原生检查。本轮额外运行 10 个合成边界／故障场景，发现 8 类可复现问题，并测量修订快照增长；退出码问题分别验证了直接脚本和完整启动链路。未重新运行完整回归，也未进行 Claude CLI 的实际交互续聊或 Linux 验证。

## 已复现问题

| 编号 | 优先级 | 问题 | 用户影响 |
|---|---|---|---|

| R-02 | P1 | 恢复文件后原生 SQL 失败，重试不具备幂等性 | 文件回来了，但原生 resume 记录缺失且无法一键重试 |

### R-01：删除异常路径可能丢失转录

位置：[trash.py](../trash.py)，`remove_item()`、`delete()`，重点为第 270、282、321、331 行。

删除先移动转录、移除原生线程，再更新缓存。`remove_item()` 完全成功后，调用方才把文件加入 manifest。如果缓存操作抛出 `OSError`，此项尚未登记；当 manifest 没有其他成功项时，`delete()` 的 `finally` 直接递归移除回收站目录，连同已移入的转录一起删除。Claude 移动侧目录失败等路径也需要同类检查。

复现：对合成 Codex 会话的 `remove_cache_lines()` 注入一次 `OSError`。结果为原文件不存在、原生线程不存在、回收站条目数为 0、回收站剩余转录数为 0。忙锁返回 `None` 与这里的抛出异常不同，不能把所有缓存忙锁都归为此结果。

建议：移动前持久化操作意图及文件身份；每一步记录阶段。缓存失败保留转录和恢复信息，不能按“成功项数量为 0”判断整个目录可删除。只清理确认没有移动过文件的空目录。补齐缓存 IO 失败、Claude 侧目录失败、manifest 写入失败及进程中断测试。

### R-02：恢复中途失败后无法正常重试

位置：[trash.py](../trash.py)，`restore()`，第 374、377、381 行。

恢复先把转录移回原路径，再恢复 SQL／缓存。SQL 失败时 manifest 保留该项，但 stored 文件已经被移走。再次恢复会因“原位置已有文件”停止，无法完成剩余的原生记录恢复。

复现：对合成会话的 `native_restore()` 注入 `sqlite3.OperationalError`；首次和第二次恢复数量均为 0。原文件存在，原生线程不存在，stored 文件不存在，第二次错误为已有文件阻挡。

建议：增加文件／SQL／缓存的分阶段恢复状态。只有 hash 和身份匹配本次恢复的已有文件才可继续修复剩余步骤；用户新写入的文件仍应拒绝覆盖。或者在失败时完整回滚，但必须同时处理 SQL 和侧目录，不能只回滚转录。

### R-03：自定义脚本退出码在内层丢失

位置：[launch_runner.py](../launch_runner.py)，`command()`，第 30–32 行；[launch_job_runner.py](../launch_job_runner.py)，`checked_inner()`／`run()`。

外层 runner 已转发退出码，但自定义 `.ps1` 会先经过另一层 PowerShell。该层仅执行脚本，没有转发脚本内部原生命令留下的 `$LASTEXITCODE`。外层得到的可能已经是错误的 0。

复现一：合成 `.ps1` 只包含 `cmd.exe /c exit 17`，通过 `launch_runner.command()` 执行，观测退出码为 0。

复现二：将此脚本作为 Codex 类型配置，走实际 Python／PowerShell 命令链路和临时生命周期；runner 返回 0，报告为 `exited`，临时目标被回收。复现使用合成原生 SQL，持久版本验证替换为测试对象，没有调用真实 Agent。

建议：内外层采用一致的退出码传递约定，说明脚本自主处理错误时的行为；不能只检查最外层 shell。补齐“脚本调用命令失败但未显式 exit”“脚本自身显式退出”“脚本异常”“批处理”与生命周期联动测试。

### R-04：等长／增长重写没有重建全文索引

位置：[agent_history.py](../agent_history.py)，`collect()`，第 287 行，及 `ingest()`。

当前通过 size／mtime 判断文件变化，但仅当新文件大小小于旧 offset 时重建。文件等长重写时，从旧文件末尾继续读取，没有重新解析被修改的旧记录；增长重写也可能只读到重写后的尾部。

复现：将合成用户文字替换成相同 UTF-8 字节长度的另一段文字，更新 mtime，再 collect。实际文件已经改变，数据库消息仍是旧文字。

建议：记录足以验证已读取前缀的 fingerprint，并区分追加、截断、替换和重写。可复用版本存储中的重写识别，但消息索引也必须同步重建。不要以任意同 ID 文件替换所选物理版本。

### R-05：接入范围只在部分入口生效

位置：[agent_history.py](../agent_history.py)，`discover()`；[conversation_store.py](../conversation_store.py)，`sync_all()`、`members()`；[history_ui.py](../history_ui.py)，版本选择。

文件发现和列表读取会应用 `sources.json`；版本同步则遍历全部已登记的物理版本，未应用同一范围。已停用来源仍会被读取，仍参与版本／分支数量及右栏版本选择。

复现：先登记 a → b 接续，再将接入范围改为只选 a。`sync_all()` 仍读取 a、b，逻辑成员仍包含 a、b，列表显示 2 个版本。

建议：建立共用的来源可用／接入状态，区分停用、缺失、已删除和已回收。停用后保留既有关系与快照，但不自动读取或修改该来源；重新接入时恢复同步。正在运行的已授权任务如何收尾需要明确约定，而不是直接当作已删除。

### R-06：任务处理不能使用展示数量上限

位置：[launch_jobs.py](../launch_jobs.py)，`reconcile()` 第 101 行、`mark_collected()` 第 111 行；[handoff_lifecycle.py](../handoff_lifecycle.py)，`retry_pending()`。

中断检测只检查最近 100 份报告。超过这个范围的死进程任务仍保持 `running`；生命周期看到此状态便跳过处理，手动重试也会跳过。

复现：创建一个运行中但进程已不存在的任务，再创建 101 份较新报告；将进程存活检查替换为 false 后 reconcile，旧任务仍为 `running`。

建议：UI 最近记录可限量，后台处理应查询所有未完成任务，并按状态／时间分批推进。优先将任务状态作为统一库中的权威记录，JSON 用作诊断输出；至少为现有 JSON 更新增加并发控制及状态转换检查。后者目前是代码层面的竞争风险，尚未复现实际 UI／runner 的竞态调度。

### R-07：元数据变动与消息分支需要分开

位置：[handoff_lifecycle.py](../handoff_lifecycle.py)，`finish()` 第 307 行；[conversation_store.py](../conversation_store.py)，`observe()`。

并行续聊判断比较整个原生快照的修订 ID。追加原生元数据也会生成新修订，因此没有新对话事件也可能触发“原平台也有新增内容”。

复现：准备接续后，仅给原平台追加 `session_meta`。前后规范事件完全相同，自动同步仍被阻挡。本轮未证明每次真实 Codex resume 都会触发这一现象。

建议：分开比较对话事件、压缩／上下文状态和普通运行元数据。需要人工确认的元数据冲突应明确说明，不能一律称为双方新增消息；保持快照不可变并继续保留原生上下文。

### R-08：单条会话失败的范围过大

位置：[launch_job_runner.py](../launch_job_runner.py)，第 44–47 行。

退出采集调用 `sync_all()` 后，只要任意版本读取失败，就在处理本任务之前抛错。无关对话的文件不可读，也会阻止本次任务创建持久承接版本。

复现：合成任务正常退出 0，另一个独立对话在版本读取时抛出 `OSError`。本任务同步状态为 failed，未创建持久版本。临时副本仍保留，没有因此丢失内容。

建议：按逻辑对话或任务依赖隔离错误。当前任务的来源、临时目标、原平台及其必要祖先必须完整验证；无关失败单独记录，不阻挡当前任务收尾。全局 collect 本身的失败也需要区分范围。

## 优化建议

### A：减少 UI 主线程中的文件读取

`history_ui.list_rows()` 在分页前处理全部物理文件；全文筛选和按轮数排序还会调用 `file_messages()` 读取历史。`on_select()` 在 Tk 主线程加载完整消息，最后只展示最近 400 条；`update_preview()` 为每个入口重新打开数据库并构造计划。`conversation_store.tips()` 为所有版本读入完整快照后做前缀比较。

建议先完善以物理文件身份为键的索引，把标题／目录／轮数／全文搜索／排序放到查询层；逻辑对话是该索引之上的归组视图。后台读取消息和准备菜单，使用请求序号丢弃过期结果；缓存按文件 fingerprint 和配置版本失效。最终启动仍重新核对文件及目标身份。对话末尾分页也要避免每次先读取全部正文。增加搜索、切换会话、启动计划及数据库锁等待的耗时测量，优化目标应基于实际数据而非仅缩放测试。

### B：控制修订、投影和任务记录的增长

每次原生内容变化，`conversation_store.observe()` 都保存完整 records、raw、events；不可变修订和投影目前没有维护策略。

测量：合成会话连续 80 次追加／修订，最终 JSONL 为 106,447 字节，80 份快照为 13,718,529 字节，约为最后转录的 128.9 倍。该值仅说明完整快照重复保存的增长方式，不是当前生产数据库的空间统计，也不代表所有真实会话都会有相同比例。

建议使用共享内容块／增量事件与周期性完整检查点，或先压缩旧快照。维护时先清理可重建投影和已完成诊断记录，并建立引用扫描、dry-run、保留期及结果报告。head、baseline、父修订、发布意图和临时任务仍有引用的快照不能直接删除。SQLite 索引压缩应单独处理，并保留导入映射、删除记录和逻辑关系。

### C：统一任务状态和配置发布

当前任务状态分别存在 SQLite 的 `temporary_handoffs` 与多个 JSON 报告中；配置由 registry、启动配置、来源范围三个文件顺序发布。原子替换单个文件不等于整体事务。

建议声明权威状态来源和允许的状态转换，记录进程身份／开始时间、失败阶段、重试次数与依赖。为多文件配置增加发布事务／恢复日志或完整配置快照。CLI 与 UI 同时改配置时应检测版本冲突，不能只依赖最后一次文件替换。

### D：安装操作应可预览、可回退

`integrations/install.ps1` 会依次改 common 配置、PowerShell profile、用户启动脚本、快捷命令，再注册 Claude MCP／hook；较后步骤失败没有整套回滚。默认快捷命令仍写死 openai1／openai2 等连接名。已经由 UI 创建的本机直接连接可能采用其他名称。

建议安装前显示将写入的位置，备份受影响配置，拆分查看器／启动器／MCP／hook／计划任务的可选项；使用实际 registry 生成或配置别名。记录安装版本、所用 Python 和组件清单，升级／卸载依据该清单操作。使用干净临时用户环境验证部分失败、重复安装和已有个人命令保留。

### E：把计划说明与任务结果分开显示

`update_preview()` 会重新设置 `launch_status`，可能覆盖任务报告或同步结果；源代码和隐形 UI 调试中可观察到刷新后状态再次变成启动计划说明。本轮没有新增独立的状态覆盖故障断言。

建议右栏分别显示“将如何启动”和“最近一次执行／同步结果”，后者保留到用户切换任务或主动关闭。提供所有未完成任务的入口；失败操作跳转到具体任务和对应平台版本，避免用户只看到通用“可重试”。版本数量与分支含义提供简短说明，临时、历史和持久承接版本使用不同标签。

### F：维护接口、目录和测试边界

保留当前单仓库结构，逐步拆分 UI 列表／阅读器／启动控制器、数据采集、原生适配、生命周期及平台操作。用 dataclass 或明确字段契约区分逻辑对话 ID、物理版本 ID、修订 ID、原生会话 ID 和任务 ID，减少多个 `dict['id']` 的混淆。平台差异集中到 Windows／Linux 接口，避免核心生命周期直接调用 PowerShell。

增加带版本的数据库迁移和 schema 能力检测；查询连接与初始化／迁移连接分开，减少主线程重复执行 DDL。对原生 Codex 格式升级继续做隔离 list／resume／内容校验。Claude 的真实交互恢复仍需独立验证，不能从 JSONL 校验推断已经完全通过。

现有测试对正常路径和部分异常保护覆盖较好，但本轮复现说明还缺跨步骤故障注入、实际嵌套 shell 退出码、等长重写、停用来源和超过报告上限的用例。后续修复应补这些回归；不需要为纯文字／布局调整机械堆测试。

性能调整：

- 用物理文件身份、祖先边界与文件变化标记缓存目录、标题、轮数和正文搜索；未变化版本同步跳过完整解析，分支比较读取事件 ID。
